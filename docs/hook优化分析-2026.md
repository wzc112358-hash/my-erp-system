# ERP 后端 Hook 问题分析与优化方案（2026-07）

> 基于完整阅读 13 个 hook 文件（共 1990 行）的实地分析。
> 核心结论先行：**当前 hook 能用，但有几个真实问题，按优先级处理。**

---

## 核心结论（先看这个）

| 问题 | 严重程度 | 是否影响业务 | 修复成本 |

| **① 写放大：一次用户写=3~6 次 DB 操作** | 🔴 高 | 是（锁竞争主因） | 中 |

## ① 写放大问题（最重要，和卡死直接相关）

### 现象

**用户每写一条子记录（收款/发票/付款/发货），实际触发 3~6 次数据库操作。** 这是 SQLite 单写锁架构下最容易撞锁的设计。

### 量化分析

以「用户创建一张销售收款」为例，hook 触发的 DB 操作链：

```
用户点保存
  ├─[写1] sale_receipts 插入用户记录
  │
  │  ← 触发 OnRecordCreate(sale_receipts) hook：
  ├─[读1] sales_contracts 查父合同
  ├─[读2] sale_receipts 查同合同所有收款（求和）
  ├─[写2] sale_receipts 更新本记录的 receipted_amount/percent  ← 同一条记录又写一次！
  │
  │  ← 触发 OnRecordAfterCreateSuccess(sale_receipts) hook：
  ├─[读3] sales_contracts 再查一次父合同  ← 重复读！
  ├─[读4] sale_receipts 再查一次所有收款  ← 重复读！
  └─[写3] sales_contracts 更新父合同的 receipted_amount/percent/status
```

**1 次用户写 = 3 次写 + 4 次读。** 几个人同时操作时，写操作排队等锁，容易卡顿。

### 问题根源

1. **before-save hook 写本记录是多余的**：第 [写2] 步把 `receipted_amount` 写回 `sale_receipts` 本身，但这个值完全可以在前端展示时计算，不需要存。存了就要多一次写。
2. **after-create hook 重复查询**：[读3][读4] 和 [读1][读2] 查的是同样的数据，因为 hook 分成了 `OnRecordCreate` 和 `OnRecordAfterCreateSuccess` 两段，各自独立查。
3. **父合同写回无法避免**（这是业务需要——合同进度要实时更新），但可以优化查询。

### 优化方案（按改动成本排序）

#### 方案 A：合并 before-save 和 after-create 的查询（低成本，推荐先做）
把 `OnRecordCreate` 里查合同+查子记录的逻辑挪到 `OnRecordAfterCreateSuccess`，避免重复读。改动小，收益直接。

#### 方案 B：取消「写本记录的派生字段」（中等成本）
`sale_receipts` 表存的 `receipted_amount`/`receipt_percent`/`debt_amount`/`debt_percent` 这些字段，本质是「这条收款所属合同的进度」，不是「这条收款本身的属性」。存到子记录上既冗余又多一次写。
- 短期：保留（前端可能在用）
- 长期：前端改为从父合同的 `expand.sales_contract` 读这些值，子记录不再存

#### 方案 C：异步更新父合同（高成本，不推荐现在做）
把「更新父合同进度」放到后台 goroutine，用户写完子记录立即返回，父合同延迟几百毫秒更新。
- 优点：用户感知的写延迟降到最低
- 缺点：实现复杂（要处理失败重试、一致性），10 人规模没必要

**我的建议：先做方案 A**（合并查询），方案 B 作为前端重构时顺便做，方案 C 不碰。

## ② Update hook 重复读 oldRecord

### 现象
8 个业务文件的 `OnRecordUpdate` 通知逻辑里，都有这样一段：

```go
// 已经在 hook 里能拿到新值了，却还要去数据库再查一次「旧值」
oldRecord, _ := GetRecordById(app, "sale_receipts", e.Record.Id)
oldStatus := oldRecord.GetString("manager_confirmed")
```

### 问题
- `GetRecordById` 是一次完整的 DB 查询，**每个 update 都多一次读**
- 目的是判断「状态是否从 pending 变成 approved」来触发通知
- 但 PocketBase 的 `RecordEvent` 在某些版本提供 `e.Record`（新值）和原始记录的对比能力，不需要再查库

### 优化方案
PocketBase 0.36 的 `OnRecordUpdate`（before-save）触发时，`e.Record` 是即将保存的新值，数据库里还是旧值。所以 `GetRecordById` 查到的确实是旧值——**逻辑没错，但可以更高效**。

可以用 `OnRecordAfterUpdateSuccess` + 对比 `e.Record` 的新旧字段（如果 PocketBase 暴露了 original），或者接受这一次额外读（毕竟 update 不是高频操作）。

**结论：这个不紧急**，update 频率远低于 create，多一次读影响不大。如果以后要优化，统一处理。

## ③ before-save hook 写本记录的设计问题

### 现象
`OnRecordCreate`（before-save）里，hook 既设置了 `manager_confirmed="pending"` 这种**合理的默认值**，又设置了 `receipted_amount`/`receipt_percent` 这种**从父合同算出来的派生值**。

```go
// 合理：设置默认状态
e.Record.Set("manager_confirmed", "pending")

// 别扭：把父合同的进度算出来存到子记录上
e.Record.Set("receipted_amount", totalAmount)  // 这是合同级的汇总，不是这条收款的属性
e.Record.Set("receipt_percent", receiptPercent)
```

### 问题
- 语义混乱：`receipt_percent` 存在收款记录上，但它代表的是「合同的收款进度」，不是「这条收款的进度」
- 数据冗余：同一个值同时存在子记录和父合同上，更新时要同步两处
- 这就是问题 ① 的根源

### 优化方案
属于方案 B 的一部分，需要配合前端改造。短期不动。

## ④ 汇率通知无去重

### 现象（settings.go 第 13-46 行）
每次更新 `settings` 表的 `default` 记录，都会给所有 sales + purchasing 用户发通知。

```go
app.OnRecordAfterUpdateSuccess("settings") → 只要 key=="default" 且 usd_to_cny 变了就发通知
```

### 问题
- 经理如果手滑连续点了多次保存，或者前后台同时更新，**会连发多条相同通知**
- 没有判断「汇率是否真的变了」（可能保存了但值没变，也发通知）

### 优化方案（低成本）
1. 对比新旧 `usd_to_cny` 值，只有**真正变化**才发通知
2. 可选：加个简单的去重窗口（比如 1 小时内同样的汇率不重复发）

```go
// 伪代码
oldRate := oldRecord.GetFloat("usd_to_cny")  // 需要拿到旧值
newRate := e.Record.GetFloat("usd_to_cny")
if oldRate == newRate {  // 值没变，不发
    return e.Next()
}
```

**建议：低优先级，但改起来简单，可以顺手做。**

## ⑤ opportunity.go 属于废弃系统

### 现象
`opportunity.go`（139 行）注册了 6 个 hook，全部针对 `monitor_sources`/`monitor_runs`/`bid_opportunities`/`opportunity_reviews` 表——这些是**你已废弃的招投标采集系统**的表。

### 问题
- 代码占空间，增加维护负担
- 虽然这些 hook 几乎不会触发（没人写这些表了），但每次启动都注册，浪费一点内存

### 优化方案
既然招投标系统废弃了：
1. **保守**：注释掉 `main.go` 第 23 行 `RegisterOpportunityHooks(app)`（一行改动）
2. **彻底**：删 `opportunity.go` + 从 `main.go` 移除注册 + 考虑删相关表

**建议：先注释注册行（保守方案），表和数据先留着。** 另外 `erp-opportunity-agent` 和 `erp-collector-service` 两个容器（占 112M 内存）也可以停掉。

## ⑥ 错误处理不统一

### 现象
hook 里遇到错误有两种写法混用：

```go
// 写法 A：记日志，继续执行（大部分 hook 用这个）
if err != nil {
    log.Printf("...failed: %v", err)
    return e.Next()  // ← 吞掉错误，请求成功
}

// 写法 B：返回错误，阻断请求
if err != nil {
    return err  // ← 请求失败，用户看到报错
}
```

### 问题
- 不一致：有时 hook 内部查询失败会吞掉错误（用户以为成功了，但数据可能不一致）
- 比如 `OnRecordCreate(sale_receipts)` 里查父合同失败 → 吞掉错误继续 → 派生字段没算对但记录还是存了

### 优化方案
统一原则：
- **查询失败（非业务错误）**：记日志，用合理默认值继续（保证用户能保存）
- **业务校验失败**（如超额）：返回错误，阻断保存
- **建议**：加一个统一的 `logHookError(app, hookName, err)` 辅助函数，规范日志格式

**优先级低，但能提升可维护性。**

## 优先级排序（实操建议）

### 🔴 P0：和卡死相关（做方案 A）
1. **合并 before-save 和 after-create 的重复查询**（问题①的方案 A）
   - 改 8 个业务文件，把 OnRecordCreate 里的查询逻辑挪到 OnRecordAfterCreateSuccess
   - 减少 2 次读操作/每次写
   - 收益：直接降低锁竞争，缓解卡死

### 🟡 P1：简单且有价值
2. **汇率通知加去重**（问题④）—— 改 settings.go，10 分钟
3. **停掉废弃的招投标 hook 注册**（问题⑤）—— 注释 1 行
4. **停掉 opportunity-agent + collector-service 容器**—— 省 112M 内存

### 🟢 P2：长期重构（前端配合时做）
5. **派生字段不再存子记录**（问题①③的方案 B）—— 需要前端配合改
6. **错误处理统一**（问题⑥）

## 关于"要不要现在改"的建议

**P0（合并查询）** 是唯一和卡死相关的优化，但它**改 8 个文件**，需要重新编译部署，有一定回归风险。

**我的建议：**
- 你现在内存已经释放了（清理 runner + agent 后可用 879M），卡死风险已经降低很多
- **先观察一段时间**——如果清理后不再卡死，说明根因就是内存，hook 优化可以慢慢做
- 如果还卡，再做 P0 的合并查询优化

**不要为了优化而优化。** 你的系统现在能正常跑，数据量小，最该做的还是先把 OSS 备份搞了（那是数据安全的底线），hook 优化是锦上添花。
