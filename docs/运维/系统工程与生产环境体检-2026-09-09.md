# ERP 系统工程与生产环境体检

日期：2026-09-09  
范围：`frontend`、`backend`、`agent-service`、Docker/Traefik、北京/兰州生产数据库、附件、日志和备份  
方式：源码静态审查、本地测试/构建、生产只读查询、HTTP 黑盒检查。角色提升验证仅在生产数据库快照上进行，未写入真实生产库。

## 结论摘要

系统当前没有表现出数据库损坏、附件被随机删除、SQLite 持续锁库或服务器持续 OOM。真正需要优先处理的是权限边界：生产 `users` 集合允许匿名注册并由请求填写角色，普通员工还可更新自己的角色。在数据库快照中已验证销售账号可以把自己改成经理。生产 `settings` 又允许匿名增删改，攻击者可改汇率并影响报表。两项都应按 P0 紧急修复。

员工所说的“数据不见了”还有一个可复现的软件层原因：多个详情/进度接口把查询异常转换为 `[]`，界面会把“加载失败”显示成“没有记录”。另外兰州库两份销售合同的父表进度与实际子记录总和不一致，会令列表、流程图和报表显示不同结果。

生产可用性目前尚可：全部容器运行正常、无 OOM/重启，数据库校验通过，1,285 个附件引用全部存在。但异地 OSS 备份连续失败，Traefik 管理面板暴露公网，容器没有健康检查，自动发布流程与真实目录结构不一致。这些问题会显著放大下一次事故。

## P0：立即处理

### SEC-01 匿名注册、员工自升经理

- 严重度：Critical
- 位置：生产北京/兰州 `_collections.users`；前端角色判断见 `frontend/src/routes/index.tsx:61`
- 证据：
  - `listRule/viewRule/createRule` 均为空字符串，即公开访问；无登录请求可列出 12 个用户的 ID、姓名和角色。
  - `updateRule = id = @request.auth.id`，只限制“修改自己”，未限制可修改字段。
  - `type` 是非隐藏、必填 select，值包含 `sales`、`purchasing`、`manager`。
  - PocketBase 全局 `rateLimits.enabled = false`，公开注册和登录接口没有应用级限流。
  - 在生产数据库副本上使用真实销售账号 PATCH 自己，结果为 `before=sales, after=manager`。
  - 源码没有针对 `users.type` 的服务端更新钩子；`ProtectedRoute` 只是前端导航控制，不能代替后端授权。
- 影响：任何人都可注册经理账号；已有员工或被盗员工令牌可获得经理权限，浏览数据安全日志、恢复记录、操作库存和执行经理接口。
- 修复：关闭公开注册；用户创建和角色变更仅允许超级管理员/专用经理管理接口；增加 `OnRecordUpdateRequest("users")` 字段级保护；使用户列表至少要求已登录，并只返回业务必要字段；回查已有用户角色变化。
- 临时缓解：立即把 `users.createRule` 设为 locked，把 `users.updateRule` 改成禁止 `type`、`verified`、邮箱等权限字段变化；在修复前轮换高权限令牌。

### SEC-02 汇率配置可被匿名修改或删除

- 严重度：Critical
- 位置：生产北京/兰州 `_collections.settings`；消费端涉及 `frontend/src/lib/exchange-rate.ts` 和利润/报表模块。
- 证据：`settings` 的 list/view/create/update/delete 五项规则均为空字符串；无登录请求可读取 `usd_to_cny`。
- 影响：匿名请求可以篡改或删除汇率，进而影响跨境合同金额、利润、报表和通知；也可制造业务不可用。
- 修复：读取权限限定为登录用户，所有写权限仅限经理；后端校验唯一 `default` 记录、合理汇率范围并记录审计日志。

## P1：本周处理

### SEC-03 业务授权范围过宽，可跨部门编辑和自行确认

- 严重度：High
- 位置：生产所有主要业务集合的 API Rules；确认钩子示例 `backend/hooks/sale_invoice.go:107`、`backend/hooks/purchase_invoice.go:116`；删除权限 `backend/hooks/recycle_bin.go:109`
- 证据：销售/采购合同及六类子记录的 createRule、updateRule 都只是 `@request.auth.id != ''`。客户、供应商、投标、费用、服务等也是任意登录用户可 CRUD。更新钩子会响应 `manager_confirmed`，但没有验证操作者必须是经理。
- 影响：绕过前端后，销售可改采购数据、采购可改销售数据；员工可把自己的确认状态改成 `approved`；同部门员工可将别人的合同和子记录移入回收站。
- 修复：把权限矩阵落实到 PocketBase Rules 和 Go 请求钩子。经理可全量操作；销售只可写销售域、采购只可写采购域；`manager_confirmed` 仅经理可改；普通员工删除至少限制 `creator_user = @request.auth.id`，或统一改为经理审批删除。
- 注意：库存写入已有 Go 经理校验，合同关联也已有角色钩子，这是正确模式，应扩展到其他业务集合。

### OPS-01 异地备份失效，现有备份与生产同盘

- 严重度：High
- 位置：生产 `/root/my-erp-system/scripts/erp-backup.sh`
- 证据：每天 02:00 的 SQLite 在线备份与附件打包成功，但 OSS 上传连续返回 `403 AccessDenied`，重试 9 次后仅保留 `/root/my-erp-system/backups/daily-local` 最近 7 份。2026-09-08 备份约 533 MiB；已完成 gzip、目录清单和两份数据库 `quick_check`，均正常。
- 影响：服务器磁盘损坏、主机误删或入侵会同时失去在线数据和所有有效备份。脚本也未备份 `auxiliary.db`，HTTP 取证日志无法从备份恢复。
- 修复：修复 OSS RAM 权限/AccessKey/桶策略；上传后做远端存在性和校验和验证；增加失败告警；至少每月做一次独立目录的恢复演练；按取证要求决定是否纳入 `auxiliary.db`。
- 补充：日志内容重复，是脚本 `tee -a` 与 cron 再次追加同一个文件造成，不影响备份内容，但应清理。

### SEC-04 Traefik 管理面板暴露公网，代理版本停止安全支持

- 严重度：High
- 位置：`docker-compose.yml:104`、`traefik/traefik.yml:5`
- 证据：`api.insecure: true`，宿主机映射 `0.0.0.0:8080`，INPUT 默认 ACCEPT；从外部访问 `http://182.92.78.227:8080/dashboard/` 返回 200。当前镜像为 `traefik:v2.9`（实际 2.9.10）。Traefik 官方支持表显示 2.9 已于 2023-04-24 结束支持且无安全支持：[官方版本支持表](https://doc.traefik.io/traefik/v2.11/deprecation/releases/)。
- 影响：公开暴露路由、服务和容器拓扑；旧版本不再接收安全修复。服务器日志已显示持续的公网扫描。
- 修复：移除 8080 宿主机映射并关闭 insecure dashboard；确需面板时只绑定 `127.0.0.1` 或通过带认证的 HTTPS 路由/VPN；按迁移指南升级到受支持版本并固定精确镜像版本或 digest。

### DATA-01 查询失败被伪装成“没有数据”

- 严重度：High（数据可信度/员工体验）
- 位置：`frontend/src/api/comparison.ts:592`、`frontend/src/api/comparison.ts:911`、`frontend/src/api/progress.ts:44`
- 证据：发货、到货、收付款和发票查询使用 `.catch(() => [])` 或空分页对象。权限、网络、过滤表达式或服务异常时，流程图和详情页会正常渲染空列表。
- 影响：员工会认为先前创建的记录被删除；经理可能按错误的空数据或待确认数量作判断。这与近期“创建过、后来找不到”的主观表现高度一致，但不能解释数据库里从未出现过的历史合同。
- 修复：禁止把非取消类错误转成空数据；使用 `Promise.allSettled` 展示“部分数据加载失败”和重试按钮；报表/流程图只在所有必要数据成功后给出完整状态，并记录关联 request ID。

### DATA-02 合同父表进度与子记录不一致

- 严重度：High（财务展示正确性）
- 位置：聚合逻辑 `backend/hooks/sale_invoice.go:63`、`backend/hooks/sale_receipt.go:66`、统一重算 `backend/hooks/contract_operations.go:466`
- 证据：数据库完整性正常，但兰州存在：
  - `LZX2604019`：父表已开票 569,700，活动发票合计 0。
  - `LZX2606033`：父表已开票 90,000、已收款 45,000，活动子记录分别合计 60,000、30,000。
  - 北京所有受检聚合一致。
- 影响：合同列表、流程图、首页进度、月利润/导出若读取来源不同，会展示互相矛盾的数字。
- 原因判断：更像历史导入/旧删除逻辑留下的冗余字段漂移，而非 SQLite 损坏。现有普通合同编辑不会提交这些进度字段，审计日志启用前的来源无法仅靠当前库还原。
- 修复：把子记录作为唯一事实来源；提供幂等“全库重算并先预览差异”的管理任务；父表聚合字段改为后端专有字段，客户端无权提交；每天巡检差异并告警。执行修复前应由经理确认这两份合同的真实业务数据。

### ENG-01 自动发布流程已停用

- 严重度：High（变更/恢复风险）

## P2：随后改进

### AUTH-01 切换北京/兰州时没有清理旧会话

- 严重度：Medium
- 位置：`frontend/src/lib/pocketbase.ts:28`、`frontend/src/stores/auth.ts:6`、`frontend/src/pages/SystemSelect.tsx:8`
- 证据：`switchSystem` 只改变 `erp_system` 和 `pb.baseUrl`，没有清理 PocketBase authStore 与 Zustand 持久状态；`PublicRoute` 看见旧 `isAuthenticated` 后会直接跳回首页。
- 影响：跨区域切换可能携带另一套库的用户 ID/令牌，表现为登录页闪退、数据加载失败、权限异常，清缓存或退出后才恢复。
- 修复：系统切换前原子执行 logout/clear，两套系统使用独立 auth storage key；启动时对当前区域执行 `authRefresh`，失败则明确返回登录页。

### OBS-01 审计窗口短，失败原因仍不够可用

- 严重度：Medium
- 位置：`backend/hooks/business_record_audit.go:53`、`frontend/src/api/recycle-bin.ts:131`
- 证据：完整的创建/修改审计从 2026-09-05 部署后才开始；更早只有 2026-08-28 起的部分关联合同日志。兰州现有 82 条，北京 0 条，并有 1 条空白异常日志。HTTP 日志只保留 5 天，且备份不包含 `auxiliary.db`。失败日志保存的是 `Failed to create record.`，真实字段原因只存在短期 HTTP 日志的 `details` 中。
- 影响：经理看见的日志少且无法解释失败；数周后的“数据丢失”投诉缺少可追溯证据。
- 修复：审计中提取并保存字段级错误、请求 ID、区域、来源页面和关键旧/新值；修复空白记录；审计表制定 1 至 3 年保留策略；HTTP 日志至少 30 天并脱敏/归档。当前代理后真实客户端 IP 未配置，日志只看到 Docker 网关 IP，启用限流前需正确设置 trusted proxy。

### PERF-01 全量加载和固定上限会随数据增长退化

- 严重度：Medium
- 位置：`frontend/src/api/comparison.ts:180`、`frontend/src/api/sales-shipment.ts:16`、`frontend/src/api/purchase-contract.ts:151`
- 证据：首页/关联合同总览一次全量拉取合同及多类子记录；多个业务列表固定读取第 1 页 500 条，详情固定 100 条；客户/供应商表单只加载前 100 个选项。当前兰州最大业务表为 183 条，尚未触顶，但增长后旧记录或选项会无提示消失。
- 影响：弱网和低配电脑打开总览越来越慢；达到 100/500 阈值后再次出现“记录不见了”。搜索字符串还直接插入 PocketBase filter，包含引号等字符时可能返回 400。
- 修复：服务端分页/筛选/聚合，远程搜索 Select，统一使用 `pb.filter` 参数化；详情改 `getFullList` 或真正分页；总览使用专门的汇总 API，不让浏览器连接七张全表。

### OPS-02 没有健康检查和告警，日志可能无限增长

- 严重度：Medium
- 位置：`docker-compose.yml`
- 证据：五个容器均无 Docker healthcheck；agent 与 Traefik 的 json-file 日志没有 max-size/max-file，前三个服务才有 10 MiB x 3 的轮转。没有发现可用性、备份或磁盘告警。
- 影响：进程“在运行但不可用”不会自动发现；公网扫描或代理异常可慢慢填满磁盘。
- 修复：为前端、两个 API、agent 添加健康检查；Traefik 依赖 healthy；统一日志轮转；增加外部探活、备份失败、磁盘 >75%、内存/Swap、容器重启告警。

### SEC-05 前端缺少浏览器安全响应头，令牌持久化在 localStorage

- 严重度：Medium
- 位置：`frontend/nginx.conf:1`、`frontend/src/stores/auth.ts:50`
- 证据：首页响应缺少 CSP、frame-ancestors/X-Frame-Options、X-Content-Type-Options、Referrer-Policy 和 Permissions-Policy；用户与 bearer token 被 Zustand 持久化，PocketBase 也维护本地认证状态。
- 影响：当前没有发现 `dangerouslySetInnerHTML`、`eval` 等明确 XSS sink，因此不是已证实可利用的 XSS；但一旦将来出现 XSS，持久令牌容易被窃取，页面也可被 iframe 嵌入诱导操作。
- 修复：先以 Report-Only 调整 CSP，再启用；补齐安全头；减少重复认证状态；评估短期令牌和重新认证策略。

### SEC-06 agent CORS 反射任意 Origin，服务持有超级管理员凭据

- 严重度：Medium
- 位置：`agent-service/src/bid/infrastructure/api-server.ts:194`、`:210`
- 证据：任意 `Origin` 会被原样写入 `Access-Control-Allow-Origin`；该公网服务同时持有北京/兰州超级管理员凭据。主要 `/api/bids/*` 请求会先验证 ERP bearer token，经理敏感操作另有角色检查；`prepare` 当前只读生成草稿。
- 影响：CORS 本身暂未形成直接越权，但扩大了令牌泄漏后的利用面；服务一旦出现鉴权绕过或 SSRF/RCE，两个区域数据库均受影响。
- 修复：Origin 白名单只允许 ERP 正式域名；把超级管理员拆成最小权限服务账号并按区域隔离；为 API 加请求大小/超时/速率限制和审计。

### SEC-07 北京 MCP 审计集合允许匿名篡改

- 严重度：Medium
- 位置：生产北京 `_collections.mcp_audit_logs`
- 证据：该集合允许匿名 list/create/update/delete；当前记录数为 0，兰州没有同名公开集合。
- 影响：暂未造成现有日志泄漏，但未来一旦写入审计记录，任何人都可读取、伪造或删除，审计结论不可信。
- 修复：读取仅限经理，写入仅限专用服务账号，客户端禁止更新和删除；将规则纳入可版本化迁移，避免北京/兰州配置漂移。

### DEP-01 前端生产依赖存在已知漏洞通告

- 严重度：Medium（结合实际可达性降级）
- 位置：`frontend/package.json:13`、`frontend/package-lock.json`
- 证据：2026-09-08 `npm audit --omit=dev` 报告 5 个受影响包（4 high、1 moderate）：直接依赖 axios 1.13.5、react-router-dom 7.13.0 及其传递依赖。axios 在 `frontend/src` 中没有被引用，其多数通告针对 Node HTTP adapter；当前项目是静态 BrowserRouter，也未使用 React Router 的 SSR/RSC 特性，因此扫描器的 high 不等于本项目已有远程 RCE。修复版本可用。
- 修复：删除未使用 axios；升级 react-router-dom 并跑完整路由回归。相关通告：[React Router advisory](https://github.com/advisories/GHSA-49rj-9fvp-4h2h)、[Axios advisory](https://github.com/advisories/GHSA-35jp-ww65-95wh)。Go 官方 `govulncheck ./...` 未发现可达漏洞；agent-service 当前无第三方运行依赖。

### DATA-03 重复合同校验存在并发竞态

- 严重度：Medium
- 位置：`backend/hooks/business_record_audit.go:100`
- 证据：创建前把整张合同表读出后在 Go 中比较规范化合同号，没有数据库唯一索引或同事务唯一约束。两次并发提交可以都通过检查。兰州当前保留 12 组重复销售合同号、8 组重复采购合同号；按现有业务决定未自动处理。

- 修复：新增 `normalized_no` 并使用数据库唯一索引；对现有重复项先由经理人工确认合并/保留策略，再启用约束。

### UX-01 大附件采用两阶段创建，失败恢复仍可更直观

- 严重度：Low/Medium
- 位置：`frontend/src/api/helpers.ts:43`
- 证据：记录先写库，再单独上传附件，这是避免 100 MiB 上传长期占用数据库写事务的合理设计。附件步骤失败时记录会保留，前端已明确提示“记录已创建，不要重复创建”。
- 影响：用户忽略提示后仍可能误以为整笔失败并重复提交；审计会出现一次创建和一次附件更新。
- 修复：失败弹窗直接提供“打开刚创建的记录/重试附件”，列表突出显示“缺少附件”；使用幂等 client_request_id；审计把附件更新单独分类。
