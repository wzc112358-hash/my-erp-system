# DATA-02 合同关系模型方案

日期：2026-09-09  
状态：仅分析，未执行数据库变更

## 结论

销售合同和采购合同都不应被定义为对方的“父表”。两者是独立业务单据，合同关联是它们之间的多对多业务关系。父子关系只存在于合同与其发货、到货、发票、收付款等执行记录之间。

当前库里的关联字段方向不能用来判断父子：系统会优先把关系写进 `purchase_contracts.sales_contract`；该字段被占用后，才可能把另一条关系写进 `sales_contracts.purchase_contract`。因此字段存在哪一侧只是实现细节，不是业务主从含义。

- `purchase_contracts.sales_contract`

目前 103 条活动关系全部存放在 `purchase_contracts.sales_contract`，`sales_contracts.purchase_contract` 为 0。现有数据实际使用的是“一份销售合同可关联多份采购合同”，尚未出现“一份采购合同关联多份销售合同”，但现有功能意图允许后者。

## 现有结构的问题

1. 同一条关系可以从两个字段表达，读取端必须取并集并去重，容易出现漏读或重复计算。
2. 两个单值字段只能依靠“另一侧还有空位”间接模拟多对多，关系写入位置不可预测。
3. 字段方向容易被误解为父子关系，但代码本身并没有稳定的父表语义。
4. 一份采购合同关联多份销售合同时，采购成本如何分摊没有业务字段。目前前端会按销售合同数量比例推算，这只是计算假设，不应作为正式财务口径。
5. 利润按每条关联分别计算后再相加，可能重复计入同一份采购合同成本。

## 推荐模型

新增 `contract_links` 关系集合，一行只表达一对销售/采购合同：

| 字段 | 说明 |
| --- | --- |
| `sales_contract` | 必填，单选关联销售合同 |
| `purchase_contract` | 必填，单选关联采购合同 |
| `allocated_quantity` | 该采购合同分配给该销售合同的数量，可空 |
| `allocated_cost_amount` | 分配成本，可空；财务确认后作为利润口径 |
| `allocation_method` | `manual`、`quantity_ratio` 等，禁止隐藏推算 |
| `created_by` | 建立关联的操作人 |
| `created` / `updated` | 建立和修改时间 |
| `deleted_at` / `deleted_by` | 解除关系的软删除审计信息 |

后端必须保证活动记录 `(sales_contract, purchase_contract)` 唯一，并校验同一采购合同的分配数量/成本合计不超过合同总量/总额。

前端展示使用“关联组”，不显示“父合同”：

- 一份销售关联多份采购：销售收入减去各关联采购的已分配成本。
- 一份采购关联多份销售：每份销售只承担关系表中分给自己的成本。
- 整组利润：组内销售收入只计一次、采购成本只计一次，再扣实际费用。
- 只有为界面折叠需要时，可给关联组设置“主展示合同”，但该字段不得参与权限、删除或利润计算。

## 迁移步骤

1. 先生成只读关系清单，覆盖活动数据和回收站数据，标记悬空、重复、数量/金额异常。
2. 新建 `contract_links`，先不删除两个旧字段。
3. 将两个旧字段的并集回填到新表，同一销售/采购组合只生成一条记录。
4. 运行双读对账：旧逻辑与新表的关联组、进度、利润逐项比较，经理处理异常清单。
5. 业务确认一对多成本分配规则；不能确认的关系标记“待分配”，月利润不得默算为正式值。
6. 切换所有新增/解除关联操作只写 `contract_links`，旧字段变为只读兼容字段。
7. 连续观察至少一个结算周期后，停止读取旧字段；最后再决定是否删除旧字段。

## 执行前验收条件

- 两套生产库完整备份已上传异地并完成一次恢复演练。
- 旧关系并集条数与新表活动条数完全一致。
- 所有悬空和重复关系为 0，或有经理签字确认的处置记录。
- 一对多、多对一各准备至少一个真实合同样例，利润和月报结果由财务/经理确认。
- 解除关联、回收站恢复、删除合同和报表导出均覆盖新关系表。
