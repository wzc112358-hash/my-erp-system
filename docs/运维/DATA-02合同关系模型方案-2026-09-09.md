# DATA-02 合同关系模型方案

日期：2026-09-09  
状态：仅分析，未执行数据库变更

## 结论

销售合同和采购合同都不应被定义为对方的“父表”。两者是独立业务单据，由“总体交易”聚合成一笔完整生意。父子关系只存在于合同与其发货、到货、发票、收付款等执行记录之间。

当前库里的关联字段方向不能用来判断父子：系统会优先把关系写进 `purchase_contracts.sales_contract`；该字段被占用后，才可能把另一条关系写进 `sales_contracts.purchase_contract`。因此字段存在哪一侧只是实现细节，不是业务主从含义。

- `sales_contracts.purchase_contract`
- `purchase_contracts.sales_contract`

目前 103 条活动关系全部存放在 `purchase_contracts.sales_contract`，`sales_contracts.purchase_contract` 为 0。现有数据实际使用的是“一份销售合同可关联多份采购合同”，尚未出现“一份采购合同关联多份销售合同”，但现有功能意图允许后者。

## 现有结构的问题

1. 同一条关系可以从两个字段表达，读取端必须取并集并去重，容易出现漏读或重复计算。
2. 两个单值字段只能依靠“另一侧还有空位”间接模拟多对多，关系写入位置不可预测。
3. 字段方向容易被误解为父子关系，但代码本身并没有稳定的父表语义。
4. 一份采购合同关联多份销售合同时，采购成本如何分摊没有业务字段。目前前端会按销售合同数量比例推算，这只是计算假设，不应作为正式财务口径。
5. 利润按每条关联分别计算后再相加，可能重复计入同一份采购合同成本。

## 推荐模型

新增 `business_deals`（总体交易）集合，每条记录直接保存该交易包含的销售合同和采购合同。一个总体交易可以是一对一、一对多、多对一或多对多；一份活动合同只能属于一个总体交易。

| 字段 | 说明 |
| --- | --- |
| `name` | 交易显示名称，默认由销售合同号生成 |
| `deal_date` | 交易归属日期，用于月利润 |
| `sales_contracts` | 交易内一份或多份销售合同 |
| `purchase_contracts` | 交易内一份或多份采购合同 |
| `tax_rate` | 建立交易时采用的利润税率快照 |
| `created_by` | 建立关联的操作人 |
| `deleted_at` / `deleted_by` | 解除最后一组有效关联时的软删除信息 |

另建 `profit_tax_rates` 保存带生效日期的税率版本，初始值和无配置兜底值均为 `0.1881`。管理新增税率版本后只影响生效日期之后新建的总体交易，历史交易保留原税率快照。

前端展示使用“总体交易”，不显示“父合同”。交易利润按组内全部销售收入减去全部采购成本、税额和实际费用计算一次，不进行销售合同之间的采购成本分摊。

## 迁移步骤

1. 先生成只读关系清单，覆盖活动数据和回收站数据，标记悬空、重复、数量/金额异常。
2. 新建 `business_deals` 和 `profit_tax_rates`，先不删除两个旧关联字段。
3. 将旧关系并集转换为连通的总体交易；同一连通组内的销售和采购合同只建立一个交易。
4. 运行双读对账：旧关系连通组与新总体交易的成员、进度、利润逐项比较，管理处理异常清单。
5. 切换所有新增/解除关联操作只写 `business_deals`，旧字段变为只读兼容字段。
7. 连续观察至少一个结算周期后，停止读取旧字段；最后再决定是否删除旧字段。

## 执行前验收条件

- 两套生产库完整备份已上传异地并完成一次恢复演练。
- 旧关系连通组与新总体交易的成员集合完全一致。
- 所有悬空和重复关系为 0，或有经理签字确认的处置记录。
- 一对一、一对多、多对一、多对多各准备至少一个样例，利润和月报结果由财务/管理确认。
- 解除关联、回收站恢复、删除合同和报表导出均覆盖新关系表。
