## 二、分问题详细分析

### 问题 1：PocketBase 继续用 vs 换独立数据库

**结论：继续用 PocketBase + SQLite，不换。**

**为什么？** 用数据说话：

| 维度 | 你的现状 | SQLite 瓶颈点 | 还有多远 |
|---|---|---|---|
| 数据量 | 3.1M（北京库） | SQLite 在 GB 级才需要关注 | **~300 倍** |
| 并发写 | 12 人，峰值几十 QPS | SQLite WAL 模式单机几百写/秒 | **够用** |
| 表行数 | 最大 21 行 | 百万行级才需考虑分表 | **~5 万倍** |
| 附件 | 73M + 239M | 看磁盘，40G 还剩 9.5G | 够 2-3 年 |

**换独立数据库（MySQL/PostgreSQL）的真实代价：**
1. PocketBase 的 Go hook 系统（你刚重构的那 8 个业务 hook）**全部要重写**为应用层逻辑
2. 部署架构复杂度：再加一个数据库容器（吃内存）、连接池、ORM
3. 迁移风险：历史数据（含中文、枚举、JSON）搬库易出错
4. 运维成本：要管 DB 备份、版本升级、慢查询
5. **而你现在没有任何一个问题是 SQLite 导致的**

**什么时候才该考虑换？**（满足任一即可重新评估）：
- 单库 > 5GB，或某张表 > 50 万行
- 写并发持续 > 100/秒（你现在远不到 1/秒）
- 需要 BI 多维分析（大量聚合查询拖慢业务）

**按你 12 人规模、几百条数据的增长速度，3 年内都不会到这个量。**

### 问题 2：数据备份（**最高优先级，立刻做**）

这是**当前最大的运维风险**：服务器上**没有任何自动备份**。一旦磁盘损坏、误删、勒索病毒，**所有业务数据永久丢失**。

**现状盘点：**
- ❌ 无 crontab 定时任务
- ❌ 无对象存储（OSS/S3）异地备份
- ❌ 无阿里云云盘快照（未配置）
- ✅ 只有我这两次部署时手动建的备份（在服务器 `/root/my-erp-system/backup/`，**和源数据在同一台机器上，机器挂了一起飞灰**）

**推荐方案：3-2-1 备份原则（3 份副本，2 种介质，1 份异地）**

#### 方案 A：阿里云对象存储 OSS 异地备份（推荐，月成本几块钱）

```
本地数据库 (ECS)  →  每日凌晨打包备份  →  上传阿里云 OSS  →  保留 30 天滚动
                       (cron + sqlite 备份命令)        (跨可用区/跨地域)
```

实现要点：
1. 开阿里云 OSS bucket（建议**异地region**，如 ECS 在北京、OSS 放杭州，防地域级故障）
2. 服务器装 ossutil（阿里云 CLI 工具）
3. 加一个 cron 脚本：每日 2:00 用 `.backup` 命令导出 SQLite（在线安全备份），打包上传 OSS
4. 保留策略：日备 7 份 + 周备 4 份 + 月备 12 份

#### 方案 B：阿里云云盘自动快照（最省事，配合 A）

- 在阿里云控制台给 ECS 系统盘配置**自动快照策略**（每日凌晨）
- 恢复时直接用快照建新盘，整机还原
- 成本：快照存储费 ~0.15元/GB/月，40G 盘约 6 元/月
- **但单独不够**：快照和源盘在同一账号，账号被入侵会一起没；必须配 OSS 异地

#### 推荐组合：A + B 都做（双保险，总成本 < 15 元/月）

**备份内容清单：**
- ✅ 两个 PocketBase 的 `data.db`（+ WAL）
- ✅ `storage/` 附件目录（73M + 239M，目前较小，每周全量即可）
- ✅ `pb_migrations/`（迁移文件，代码仓库也有）

### 问题 3：服务器挂了，数据还能找吗？

分三种故障：

| 故障类型 | 当前能否恢复 | 改进后 |
|---|---|---|
| **单个容器崩溃**（PocketBase 进程崩） | ✅ `restart=unless-stopped` 自动拉起，数据在 bind-mount 不丢 | 同 |
| **宿主机重启**（断电/维护） | ✅ Docker 自启，容器自动恢复 | 同 |
| **宿主机彻底挂了/磁盘坏/账号被黑** | ❌ **数据全丢**（本地备份也在同一台机） | ✅ OSS 异地备份 24h 内可拉回重建 |

**灾难恢复演练（建议每季度做一次）：**
1. 从 OSS 拉最近一份备份到一台新 ECS
2. 起 PocketBase 容器指向这份 data.db
3. 验证登录、看几条合同数据，确认可恢复
4. **不演练的备份等于没有备份**——很多公司等真出事才发现备份是坏的

**RTO/RPO 目标（小企业合理标准）：**
- RPO（最多丢多少数据）：< 24 小时（日备）
- RTO（多久能恢复）：< 4 小时（手动拉备份+建机器）

### 问题 4：服务器资源优化（当前最该动的）

**问题：1.6G 内存已用 75%（剩 663Mi），是当前最大隐患。** 内存一满，Linux 会 OOM killer 随机杀进程，可能杀到 PocketBase 导致服务中断。

**立即可做的优化：**

| 项 | 当前 | 建议 | 释放内存 |
|---|---|---|---|
| `pocketbase-lanzhou` 内存上限 | 800M | 降到 256M（实际只用 58M） | -544M 配额 |
| `pocketbase-beijing` 内存上限 | 384M | 256M（实际只用 49M） | -128M |
| swap 分区 | 不确定 | 建议加 2G swap 兜底 | 缓冲 OOM |

兰州库给 800M 是历史遗留（兰州业务量比北京还小，给这么多纯浪费）。

**磁盘（40G 已用 28G，剩 9.5G）：**
- 主要占用是 Docker 镜像（多次部署残留）+ 附件
- 定期 `docker image prune -a` 清理无引用镜像
- 附件目前 312M，按增长速度 2-3 年不愁

**升级建议（如果未来加 AI）：**
- 内存加到 4G（AI 应用吃内存）
- 磁盘 40G → 100G（附件 + AI 模型缓存）

### 问题 5：以后扩展 AI 应用分析怎么办

**好消息：你现在的架构对 AI 很友好，不用动后端。**

PocketBase 自动提供标准 REST API，AI 应用直接读就行：

```python
# AI 分析应用（独立部署，不碰 ERP 后端）
import requests
resp = requests.get(
    "https://api-beijing.henghuacheng.cn/api/collections/sales_contracts/records",
    headers={"Authorization": "Bearer <ERP用户token>"},
    params={"perPage": 500}
)
contracts = resp.json()["items"]
# → 喂给 LLM 做分析 / 报表 / 预测
```

**推荐的 AI 扩展架构（不动 ERP）：**

```
┌─────────────────┐     REST API      ┌──────────────────┐
│  ERP (PocketBase)│ ←─────────────────│  AI 分析服务     │
│  （只读为主）    │   带 token 读数据  │  (独立容器/服务) │
└─────────────────┘                   └──────────────────┘
                                              │
                                       调 LLM API（云端）
                                              │
                                       生成报表/洞察
```

**关键原则：AI 应用是 ERP 的「读者」，不是「侵入者」：**
1. ✅ 用专用账号 + 只读权限（你刚加的访问规则可以配一个 `ai_reader` 用户）
2. ✅ AI 服务**独立部署**，崩了不影响 ERP
3. ✅ AI 生成结果存到**新表**（如 `ai_reports`），不污染业务数据
4. ❌ 不要让 AI 直接写业务表（合同、发票），避免幻觉污染

**可能的 AI 应用方向（基于你的业务）：**
- 销售分析：「这个客户过去 3 个月采购趋势，建议怎么跟进」
- 回款预测：「这批发货的合同，预计回款时间和风险」
- 库存优化：「基于历史采购，哪些品类该提前备货」
- 异常检测：「这张发票金额偏离合同均值 2 倍，请核查」

**你现在已经有雏形：** 服务器上的 `erp-opportunity-agent`（招投标采集）就是这种模式——独立服务，读 ERP 数据。AI 分析应用照这个模式扩展即可。
